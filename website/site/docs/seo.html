Sitemaps, canonical URLs and page exclusions

ItsyWeb 0.20.0 can keep your public page list up to date for search engines. A sitemap lists the page addresses you want discovered. A canonical tag identifies a page's preferred address. Configure these once; ItsyWeb updates the generated sitemap when public content changes.

1. Check your CLI and server

Update your installed CLI and check its version:

itsy update
itsy version

This feature starts in 0.20.0 and requires matching CLI/server deployment protocol 28. If an existing server runs an older version, run the following from a site whose current Git branch has that server saved as its deployment destination:

itsy update-server

It asks before briefly restarting every site on that host. Updating the CLI or deploying website files alone does not update the server executable. A new server set up with the current CLI already receives its bundled runtime. See deployment for destination setup.

2. Set the production address

Add a top-level seo object to itsy.config.json, alongside app. This minimal example shows the placement; keep your existing app, admin, apps and deployment settings:

{
  "app": {"site_name": "Example"},
  "seo": {
    "url": "https://example.com",
    "exclude": ["/campaign/receipt"]
  }
}

Replace https://example.com with your site's production HTTPS address, even while working locally or on staging. Use only the origin: no credentials, subdirectory, query or fragment. ItsyWeb uses this configured address rather than a request Host or forwarding header. Without seo, automatic discovery is disabled. This setting does not configure DNS, register a hostname or enable HTTPS.

exclude is optional. Replace the example path with an existing page you want kept out of search, or omit the list. Entries match one exact path without wildcards, queries or trailing slashes; excluding /campaign does not exclude its descendants. Exclusion does not create a missing page.

3. Check locally, then deploy

itsy status
itsy dev

Open the local address printed by dev. Check these responses:

  • /sitemap.xml: XML containing eligible public page addresses on your production domain, with no localhost or staging URLs.
  • /robots.txt: a Sitemap: https://example.com/sitemap.xml line using your production address, unless you supply a custom file.
  • A public page: use View Source to find its rel="canonical" link. It uses the production address without tracking queries. An HTML fragment without a closing head receives a canonical HTTP Link header instead.
  • An existing excluded page: it still loads, but the browser's Network panel shows X-Robots-Tag: noindex. It has no generated canonical or sitemap entry.

Commit your reviewed configuration and site changes, then deploy from the intended branch:

itsy deploy

Normal deployment publishes the committed configuration and preserves existing live editable content. Repeat the checks on the public domain. If you use curl, check an existing excluded page's headers with:

curl -I https://example.com/campaign/receipt

Replace the address and path with your own; expect X-Robots-Tag: noindex. Excluded pages remain public. Use authentication for private information, and keep excluded pages crawlable so search engines can read the noindex header.

What ItsyWeb includes and preserves

The generated sitemap includes ordinary public pages, enabled Blog listings and published posts, and enabled Contact forms. Drafts, private/admin routes, assets, errors, managed custom apps, redirects and enabled Contact's thank-you page stay out. Contact's thank-you page receives noindex automatically. Pages with robots or googlebot noindex metadata are also omitted. There are no guessed modification dates; beyond 50,000 URLs or 50 MiB, provide a custom sitemap index.

Existing canonical tags are preserved. A page with a custom canonical enters the generated sitemap only if that tag exactly matches its absolute production URL. Relative, empty or different custom canonicals keep the page out of the generated list.

Custom site/sitemap.xml and site/robots.txt routes take precedence independently and are served unchanged. ItsyWeb does not append a Sitemap line to a custom robots.txt or remove excluded URLs from a custom sitemap. Maintain those declarations and exclusions yourself. Generated documents live in memory; you do not need to create or commit them. Redirect rules cannot use either discovery endpoint as a source while automatic SEO is enabled.

The exact-host staging policy remains separate. It still adds noindex/nofollow to staging responses, including discovery documents, while shared sitemaps and canonicals name the production origin. A production URL does not automatically protect other hostnames; configure staging policy explicitly.

Optional: tell Google where the sitemap is

Google Search Console is Google's free reporting tool for website owners. It is optional. ItsyWeb's generated robots.txt already advertises the sitemap, so Google can discover it without an account or integration in ItsyWeb.

To see whether Google has read the sitemap and reported processing errors, first make sure it is reachable on your public production domain. Then:

  1. Open Search Console and verify that you own the production domain or site address.
  2. Select that site and open Sitemaps.
  3. Submit https://example.com/sitemap.xml. If the form already supplies your site's address, enter only sitemap.xml.

You submit the URL, not an uploaded XML file. Keep the same URL as content changes; you do not need to submit it after every edit. Submission does not guarantee indexing, ranking or AI citations. See Google's sitemap guide.

Keep staging out of search

From ItsyWeb 0.19.0, configure indexing for an already registered hostname over SSH. Staging and production can serve the same website files:

itsy server indexing root@server staging.example.com noindex
itsy server list root@server

Type the exact hostname when asked. ItsyWeb sends X-Robots-Tag: noindex, nofollow on that hostname's pages, assets, app responses, errors, downloads and redirects. Aliases can have different policies. The command restarts the shared service, briefly affecting other sites.

Policy belongs to the server, outside site app settings, editable content and release files. Normal deployment, content sync, code rollback and site restore retain the current policy. itsy status and itsy server list show effective settings. Existing hostnames without a policy keep their behavior; ItsyWeb does not infer staging from the hostname.

itsy server indexing root@server staging.example.com allow

allow stops adding the framework restriction. It does not emit index, follow, remove owner-authored headers or meta tags, or guarantee search visibility. Each exact registered hostname is configured separately; wildcards and arbitrary forwarding headers cannot select a policy.

Keep robots.txt crawlable. A site-wide Disallow: / can stop crawlers discovering the noindex header. The host policy does not rewrite robots.txt, sitemaps, canonical tags or templates, and reports detected static site-wide crawl blocks. The separate SEO settings can generate missing discovery documents and canonical tags. This controls cooperative search indexing, not private access.

Removing a site clears only its own hostname policies; redeploying a removed name does not restore them. Site backups exclude host policy. Interrupted policy changes use the existing server-side sudo itsy-server -recover journal, which restores the complete prior host configuration. Upgrade both client and server to protocol 28 before using this feature. Verify the live staging header before removing any existing site-level meta fallback.
