ItsyWeb Guides

Managed apps

Understand app mounts, build a local executable, and work with app-owned sessions.

Apps

Blog is a built-in content application available from 0.15.0; see Blog setup. The service contract below applies to apps such as Contact, rather than Blog’s content storage and admin editor.

An app is a small, separate JSON service mounted at a public URL. ItsyWeb owns the public page, the HTML form, the redirect, the template values and the email; the app owns its own logic and validates its own fields. Values an app returns are request-local and are never written into your site.

Contact ships with ItsyWeb. You can also register your own managed local app package. See Building a custom app.

What you can use

  • Contact sends a visitor's message to one email address. Its configuration, form and templates are in Email & contact forms.
  • Custom apps are managed local executables registered under apps.<name> with a validated package. They can own their own sessions.
  • Remote services, public read-only routes declared in config, databases and uploads are not part of the shipped contract.
  • There is no public SDK. ItsyWeb's Go packages are private, but an app is an ordinary executable that speaks the documented HTTP/JSON contract.

Enable Contact

Merge this into itsy.config.json, keeping your other settings:

{
  "apps": {
    "contact": {
      "mount": "/contact",
      "email": {"to": "owner@example.com"}
    }
  }
}

mount is required: a canonical public path such as /contact or /deep/contact. email.to is required. Optional email.from overrides the server sender and must be authorized by your mail provider. Credentials never belong here. Remove the apps.contact entry to disable the app.

Create site/contact/index.html and a mount-relative site/contact/thank-you.html. Do not also create site/contact.html. The starter includes both pages but leaves the app disabled until you choose a recipient. Restart dev after changing app settings.

How a submission flows

  1. The visitor submits an ordinary HTML form to the mount.
  2. ItsyWeb checks CSRF, exact Origin, method, content type and size, then converts the fields to flat JSON.
  3. ItsyWeb calls the app's mount-relative route with its own private credential. Browser cookies and authorization are never forwarded.
  4. The app returns JSON. ItsyWeb redirects, re-renders with errors, or shows a safe unavailable message.

App values appear under the app name, such as contact.data.name, contact.invalid.email, contact.error and contact.flash.notice. They are escaped values, never template source.

Building a custom app

You can write an independent HTTP service that speaks the current Itsy App Protocol (version 2) in any language, then register it as a managed local executable. It receives flat JSON and returns a small JSON envelope. This section documents the contract so you can build, mount and test one.

Custom apps are available from 0.17.0. Add an apps.<name> entry with a mount, and put a validated package at itsy/apps/<name>/ containing app.json and the executables it names. There is no install command, no package registry, no url or port key and no public SDK. ItsyWeb launches only this confined local executable; remote services are not supported. Deploying an app package requires server protocol 28, so update the server first; a protocol-25 server refuses the package.

Register a package

Build your service for the server platform, then create a package. The manifest's name must match the config key, protocol must be 2, and executable maps a <goos>-<goarch> key to one filename in the same directory. Build for every platform you run (your development host and the server) and list each one:

itsy/apps/session/app.json
{"name":"session","version":"0.1.0","protocol":2,"executable":{"darwin-arm64":"session-darwin-arm64","linux-amd64":"session-linux-amd64"}}
itsy/apps/session/session-darwin-arm64
itsy/apps/session/session-linux-amd64

Enable it in itsy.config.json:

{
  "apps": {
    "session": {"mount": "/session"}
  }
}

Create a page at the mount, such as site/session/index.html. A GET reads from the app; a POST submits a form that includes {csrf}. ItsyWeb strips the mount, so /session/login calls service route /login. Restart itsy dev after changing app settings or rebuilding the executable. At handshake time ItsyWeb verifies the running service, so the manifest is not trusted as proof of compatibility.

Two boundaries

Keep the browser-to-ItsyWeb form boundary separate from the ItsyWeb-to-app call. The form is URL-encoded and bounded to 32 KiB; only POST carries a body. ItsyWeb strips the configured mount and forwards the rest of the path unchanged, so the mount itself becomes /.

Request JSON

There is no request envelope. The body is a flat object of form names:

{"name":"Alex","email":"alex@example.com","message":"Hello"}
  • A name submitted once is a string. A repeated name is an array of strings.
  • An empty field stays ""; a missing field is absent.
  • Names are literal: address.city and items[0] stay those exact keys, with no nesting.
  • Values are always strings or arrays of strings. The app converts types itself.
  • ItsyWeb verifies and removes its own _csrf field before forwarding. An app must not define it.
  • The JSON body is bounded to 192 KiB.

Response envelope

The service replies with one JSON object using only these keys:

  • data (object): app-owned values, rendered as contact.data.*.
  • invalid (object of string to string): validation messages, contact.invalid.*.
  • error (string): one operational failure message, contact.error.
  • flash (object of string to string): temporary messages, contact.flash.*.
  • redirect (string): a mount-relative destination, handled by ItsyWeb and not shown in templates.
  • session (object or null): an app-owned session instruction, not shown in templates. See App-owned sessions.

Only these keys are reserved. Unknown keys, an explicit null (except for session, where null clears the cookie), duplicate keys, a non-object body, a wrong content type or an oversized body are treated as a service failure. invalid and flash values must be strings; values inside data may be any JSON. Flash is limited to 4,096 bytes and responses to 1 MiB.

Statuses and browser outcomes

  • 200 with no invalid and no error: success. With redirect, the browser gets a 303.
  • 422 with at least one invalid and no error: the page re-renders with status 422.
  • 503 with an error and no invalid: the page re-renders with status 503.
  • Any other status or a malformed response becomes a safe 503 with a generic message.

Success:

{"redirect":"thank-you","flash":{"notice":"Your message was sent."}}

Validation:

{"data":{"email":"invalid"},"invalid":{"email":"Enter a valid email address."}}

Failure:

{"error":"We couldn't confirm delivery. Please try again later."}

Launch contract

ItsyWeb launches a managed app itself; a site configures only apps.<name>.mount and never a port, descriptor or token. The child receives three inherited descriptors:

  • fd 3: an already-bound 127.0.0.1:0 TCP listener, so there is no port race and no port in config.
  • fd 4: one JSON object with exactly five string keys: {"Name":"<app>","Token":"<64 hex>","Storage":"<private dir>","CapabilityURL":"","CapabilityToken":""}. A custom app gets empty capability values; the bundled Contact app gets a non-empty capability URL and token. Unknown fields are rejected, so declare all five.
  • fd 5: a parent-liveness pipe; EOF means shut down.

The child environment is only LANG=C, and its standard output and error are discarded so private payloads are never logged. The executable is re-opened through a confined root at launch, checked against the size and SHA-256 recorded when the site loaded, and copied to a private file before it runs; a swap after validation cannot change what runs. One child runs per site and app with bounded backoff; an unavailable app only affects its own routes.

Handshake and transport

Before any app call, ItsyWeb performs a private handshake:

GET /_itsy/handshake
Authorization: Bearer <app-token>

The service must return 200 with JSON like:

{"name":"example","version":"0.1.0","protocol":2}

ItsyWeb checks the name and protocol: 2; version is the app's own release. A manifest alone is not proof. Every call carries the bearer token; browser cookies and authorization are never forwarded. Responses must be application/json, redirects are not followed, and POSTs are never retried. The handshake deadline is 2 seconds and ordinary calls 15 seconds; at most four calls run per app and 64 process-wide, with no waiting queue.

App-owned sessions

A custom app can own its own server-side sessions; ItsyWeb stores no session data. ItsyWeb reads its own per-app cookie and sends the opaque token to the app as the X-Itsy-Session request header, never as a browser cookie or authorization header. The app's reply may add a session key: omit it to leave the cookie unchanged, use null to clear it, or set {"token":"...","max_age":86400} to set or rotate it. Tokens are 16 to 512 cookie-safe printable ASCII bytes and max_age is 1 second to 30 days. A malformed session value is rejected and no cookie changes. ItsyWeb owns the cookie name, Secure, HttpOnly, SameSite=Lax, Path=/ and the __Host- prefix. The cookie is isolated by app, and by site through host-only scoping, so a production cookie is never sent to another site's host; a malformed or duplicate cookie, including a valid cookie with a malformed duplicate of the same name, is ignored. The token never appears in templates, logs, URLs or public JSON. Store session state in the private directory ItsyWeb passes to the app at launch. It is stable per-site runtime state outside every release, excluded from releases and backups, and never pruned by ItsyWeb, so it survives a release change; back it up yourself. An app session never grants admin or editor access.

A complete managed sample

This standard-library program is a whole managed app: it reads the inherited descriptors, answers the handshake, serves a page, and owns a session cookie. Copy it into an empty directory with go.mod, build it for every platform you run, and register the package as shown above. It imports no ItsyWeb package.

// A complete managed Itsy app using only the standard library. Build it for
// every platform you run, place the files under itsy/apps/<name>/, and register
// the package under apps.<name> in itsy.config.json. Itsy launches it and speaks
// the contract below; it never imports a Itsy package.
package main

import (
	"context"
	"crypto/rand"
	"crypto/subtle"
	"encoding/hex"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net"
	"net/http"
	"os"
	"os/signal"
	"path/filepath"
	"sync"
	"syscall"
	"time"
)

const (
	protocol      = 2
	version       = "0.1.0"
	sessionHeader = "X-Itsy-Session"
	maxAge        = 3600
	maxSessions   = 1000
)

// fd 4 is one JSON object with exactly these five string keys. A custom app
// receives empty capability values; unknown fields are rejected.
type launchConfig struct {
	Name, Token, Storage, CapabilityURL, CapabilityToken string
}

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	if err := run(ctx); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

func run(ctx context.Context) error {
	configFile := os.NewFile(4, "app-credentials")
	var cfg launchConfig
	decoder := json.NewDecoder(io.LimitReader(configFile, 4097))
	decoder.DisallowUnknownFields()
	err := decoder.Decode(&cfg)
	var extra any
	end := decoder.Decode(&extra)
	configFile.Close()
	if err != nil || end != io.EOF || len(cfg.Token) != 64 {
		return errors.New("invalid launch configuration")
	}
	name := cfg.Name
	if name == "" {
		name = "example"
	}

	listenerFile := os.NewFile(3, "app-listener")
	listener, err := net.FileListener(listenerFile)
	listenerFile.Close()
	if err != nil {
		return errors.New("app listener is unavailable")
	}
	defer listener.Close()

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()
	alive := os.NewFile(5, "app-parent")
	defer alive.Close()
	go func() { _, _ = io.Copy(io.Discard, alive); cancel() }()

	app := newHandler(name, cfg.Token, cfg.Storage)
	server := &http.Server{
		ReadHeaderTimeout: 2 * time.Second,
		ReadTimeout:       15 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       30 * time.Second,
		MaxHeaderBytes:    16 << 10,
		Handler:           app,
	}
	done := make(chan error, 1)
	go func() { done <- server.Serve(listener) }()
	select {
	case err := <-done:
		return err
	case <-ctx.Done():
	}
	shutdown, finish := context.WithTimeout(context.Background(), 2*time.Second)
	defer finish()
	if err := server.Shutdown(shutdown); err != nil {
		server.Close()
	}
	<-done
	return nil
}

// handler is a tiny session service. The "login" action is a demonstration
// only: it checks no credentials and is never real authentication.
type handler struct {
	name    string
	token   string
	path    string
	mu      sync.Mutex
	tokens  map[string]int64
}

func newHandler(name, token, storage string) *handler {
	h := &handler{name: name, token: token, tokens: map[string]int64{}}
	if storage != "" {
		h.path = filepath.Join(storage, "sessions.json")
		if data, err := os.ReadFile(h.path); err == nil {
			_ = json.Unmarshal(data, &h.tokens)
		}
	}
	return h
}

func (h *handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	if len(r.Header.Values("Authorization")) != 1 ||
		subtle.ConstantTimeCompare([]byte(r.Header.Get("Authorization")), []byte("Bearer "+h.token)) != 1 {
		http.Error(w, "Unauthorized", http.StatusUnauthorized)
		return
	}
	if r.URL.RawPath != "" || r.URL.RawQuery != "" {
		writeJSON(w, 400, map[string]any{"error": "Unsupported request."})
		return
	}
	if r.URL.Path == "/_itsy/handshake" && r.Method == http.MethodGet {
		writeJSON(w, 200, map[string]any{"name": h.name, "version": version, "protocol": protocol})
		return
	}
	if r.URL.Path != "/" {
		writeJSON(w, 404, map[string]any{"error": "Unsupported request."})
		return
	}
	switch r.Method {
	case http.MethodGet:
		token := r.Header.Get(sessionHeader)
		body := map[string]any{"data": map[string]any{"authenticated": h.valid(token)}}
		if token != "" && !h.valid(token) {
			body["session"] = nil
		}
		writeJSON(w, 200, body)
	case http.MethodPost:
		h.post(w, r)
	default:
		w.Header().Set("Allow", "GET, POST")
		writeJSON(w, 405, map[string]any{"error": "Use GET or POST."})
	}
}

func (h *handler) post(w http.ResponseWriter, r *http.Request) {
	if r.Header.Get("Content-Type") != "application/json" {
		writeJSON(w, 400, map[string]any{"error": "Send JSON."})
		return
	}
	var fields map[string]any
	decoder := json.NewDecoder(http.MaxBytesReader(w, r.Body, 192<<10))
	if err := decoder.Decode(&fields); err != nil {
		writeJSON(w, 400, map[string]any{"error": "Invalid body."})
		return
	}
	action, _ := fields["action"].(string)
	switch action {
	case "login":
		token, err := h.create()
		if err != nil {
			writeJSON(w, 503, map[string]any{"error": "Could not start a session."})
			return
		}
		writeJSON(w, 200, map[string]any{"data": map[string]any{"authenticated": true}, "session": map[string]any{"token": token, "max_age": maxAge}})
	case "logout":
		if err := h.drop(r.Header.Get(sessionHeader)); err != nil {
			writeJSON(w, 503, map[string]any{"error": "Could not end the session."})
			return
		}
		writeJSON(w, 200, map[string]any{"data": map[string]any{"authenticated": false}, "session": nil})
	default:
		writeJSON(w, 422, map[string]any{"data": fields, "invalid": map[string]string{"action": "Use login or logout."}})
	}
}

func (h *handler) valid(token string) bool {
	if token == "" {
		return false
	}
	h.mu.Lock()
	defer h.mu.Unlock()
	h.expire()
	_, ok := h.tokens[token]
	return ok
}

func (h *handler) expire() {
	now := time.Now().Unix()
	for token, expiry := range h.tokens {
		if expiry <= now {
			delete(h.tokens, token)
		}
	}
}

func (h *handler) create() (string, error) {
	var raw [32]byte
	if _, err := rand.Read(raw[:]); err != nil {
		return "", err
	}
	token := hex.EncodeToString(raw[:])
	h.mu.Lock()
	defer h.mu.Unlock()
	h.expire()
	if len(h.tokens) >= maxSessions {
		return "", errors.New("full")
	}
	h.tokens[token] = time.Now().Add(maxAge * time.Second).Unix()
	if err := h.save(); err != nil {
		delete(h.tokens, token)
		return "", err
	}
	return token, nil
}

func (h *handler) drop(token string) error {
	if token == "" {
		return nil
	}
	h.mu.Lock()
	defer h.mu.Unlock()
	previous, ok := h.tokens[token]
	if !ok {
		return nil
	}
	delete(h.tokens, token)
	if err := h.save(); err != nil {
		h.tokens[token] = previous
		return err
	}
	return nil
}

// save writes durably and returns any failure so the request can fail closed.
func (h *handler) save() error {
	if h.path == "" {
		return nil
	}
	data, err := json.Marshal(h.tokens)
	if err != nil {
		return err
	}
	dir := filepath.Dir(h.path)
	f, err := os.CreateTemp(dir, ".sessions-")
	if err != nil {
		return err
	}
	temp := f.Name()
	defer os.Remove(temp)
	if _, err = f.Write(data); err == nil {
		err = f.Sync()
	}
	if closeErr := f.Close(); err == nil {
		err = closeErr
	}
	if err != nil {
		return err
	}
	if err = os.Rename(temp, h.path); err != nil {
		return err
	}
	directory, err := os.Open(dir)
	if err != nil {
		return err
	}
	defer directory.Close()
	return directory.Sync()
}

func writeJSON(w http.ResponseWriter, status int, body any) {
	w.Header().Set("Content-Type", "application/json")
	w.Header().Set("Cache-Control", "no-store")
	w.WriteHeader(status)
	_ = json.NewEncoder(w).Encode(body)
}

Try the contract locally

A compatible service can be tested without ItsyWeb. The essential flow is: require a bearer token, answer GET /_itsy/handshake with the identity above, and answer POST / with an envelope. For example, a local service could answer a handshake:

curl -s http://127.0.0.1:8787/_itsy/handshake \
  -H "Authorization: Bearer $APP_TOKEN"

and a form submission:

curl -s -X POST http://127.0.0.1:8787/ \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Alex"}'

This proves the wire contract, authentication and statuses. It does not mount the service in a site.

What remains planned

Remote (non-local) services, public read-only routes declared in configuration, databases, storage helpers and file uploads remain planned. ItsyWeb supervises only a confined local executable; it does not download packages or run arbitrary commands.
