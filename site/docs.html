FLEACMS DOCUMENTATION

Build the site and the server.

Install a single binary, build with HTML and CSS, and let Flea prepare your Ubuntu server, deploy over SSH and serve HTTPS. Mark the parts admins can edit.

The whole system

Flea is not only a content editor. It covers the developer's side of a small website and the server it runs on.

  • One binary, no dependencies. Install the CLI in a single command; there is no Go, Node, Python or database to add on your machine.
  • A local dev server. flea dev serves your files with live reload, LAN testing and local email previews.
  • Server setup. flea setup installs the bundled Flea server on a blank Ubuntu host over SSH — nothing to install by hand on the host.
  • Deployment. flea deploy publishes a committed Git branch over SSH. One host can serve many sites.
  • Automatic HTTPS. Flea requests and renews Let's Encrypt certificates and can redirect www.
  • Admin editing. Clients sign in and change text, photos, videos and repeatable lists on the page.
  • Recovery. Backups, code rollback and restore are built in.
  • Agent-friendly. Portable instructions let coding agents build and import sites with you.

Install FleaCMS

For Apple Silicon Macs and x86-64 Linux. Open Terminal and run:

curl -fsSL https://fleacms.com/install.sh | bash

The installer downloads the matching executable, checks its SHA-256 checksum and installs it to ~/.local/bin/flea. No sudo and no extra runtime such as Go, Node or Python is required. It does not change your shell profile.

Use the installed copy in this terminal and check the version:

export PATH="$HOME/.local/bin:$PATH"
flea version

If needed, add that PATH line to your shell profile for future terminals. Then follow the quickstart below.

0.19.0 is the current release for Apple Silicon Mac and x86-64 Linux. Keep staging out of search with an exact-host response header, without changing website files. Existing empty-directory creation with flea new . remains available. Linux ARM64 CLI downloads are discontinued; both supported CLIs still deploy to x86-64 and ARM64 Linux servers. Older downloads remain available at their versioned URLs. The Mac binary is ad-hoc signed, not notarized; clean-machine testing is still in progress. Intel Mac downloads are not included. Deployment protocol is 27 and the Flea App Protocol remains version 2. Run flea update to update your local CLI. Hostname indexing requires matching protocol-27 clients and servers. Update the server separately with flea update-server before deployment or host administration; a local CLI update does not upgrade the host.

You can read the installer before running it, or download the Mac binary, Linux x86-64 binary and checksums directly.

A site needs no frontend build pipeline or database. The CLI is a single binary, and the server needs nothing installed by hand either. Deployment uses Git and SSH; see Set up the server.

Your first site

Create a project and start the local server:

flea new my-site
cd my-site
flea dev

Already in an empty project folder? Run flea new ., then flea dev. You can also pass a relative or absolute directory path, such as flea new ./my-site. Flea creates a missing directory when its parent exists. Existing directories must be completely empty, including hidden files and .git; Flea refuses nonempty directories without overwriting anything. The folder name still supplies the default site name.

Enter a site name when prompted, then optionally add an admin email who can sign in and edit. You can also add one later with flea admin. Open the Website URL printed in the console. Dev starts on port 3000 and explains occupied ports before trying 3001, 3002 and so on. An explicit --port stays fixed; --port 0 lets the operating system choose a port.

Run flea dev again to replace this site’s running dev server, including when switching to -l or changing ports. Pull/reset operations are never interrupted. Stop a dev process started with an older binary manually once.

Edit site/index.html. The browser reloads when your files change. Add a little editable text:

<h1 snip>Hello, from our little corner.</h1>

While dev runs, Flea moves that text into flea/snips.json and leaves a generated reference in your HTML. Keep both files together in Git.

To start with example pages, use flea new --starter my-site. The default gives you a clean homepage.

Check your work

flea status

This validates your project without rewriting it and shows page, asset and editable-area counts plus Git state. If the current branch has a saved deployment, Flea automatically checks it over SSH, with a spinner in terminals. The output separates website reachability, deployed code and editable content. A previous pull baseline is required to identify which side changed; otherwise differences have unknown direction. Without a saved destination, status finishes locally. New projects have a Git repository on main with an Initial site commit. Flea prints commands to connect and push to your remote repository. Use --skip-git to skip Git setup. If the commit fails, the site remains usable and Flea prints instructions to retry.

Test on another device

To use a phone, tablet or another computer on the same trusted network, start dev with:

flea dev --lan

flea dev -l does the same thing. Flea prints Network and Hostname URLs for detected private/Tailscale IPv4 addresses and this computer's name/local alias. Open a printed URL, such as http://studio:3000, when that name resolves to the dev computer. Its /admin link opens sign-in. Exact Host/port and peer checks remain required. Without the flag, dev stays accessible only on your computer using the printed Website URL.

This is the full dev site: approved admins can sign in, edit text and collections, upload photos and videos, and save changes. Contact forms, browser reloads and dev diagnostics work over the network too. Each device signs in separately.

Sign-in codes and email previews

With email preview enabled, messages still open on the computer running Flea. Enter the code on your other device. To share a private preview, replace its loopback IP with the printed network IP, keeping the port and random path. Anyone with that link and network access can read the message, so keep it private. There is no public inbox.

LAN mode uses unencrypted HTTP. Use it only on a trusted network, never forward the development port, and restart dev after changing networks. VPN addresses may also appear. Your firewall must allow the selected port; guest Wi-Fi can block connections between devices. Use --port 3001 if you need a different port.

Pages & templates

Add a page

Create site/about.html for /about. You can use site/about/index.html instead, but not both. Link to extensionless URLs without a trailing slash.

Share a layout

The default wrapper is site/main.layout.html. Put {slot} where the page content belongs.

<header>Our studio</header>
<main>{slot}</main>
<footer>Thanks for stopping by.</footer>

For a different wrapper, put this comment at the very start of a page:

<!-- flea
layout: /custom.layout.html
-->

Preserve the generated layout's app.current_admin conditional blocks, CSRF meta tag and admin toolbar include. They connect the page to the admin editor.

Reuse a partial

Create site/_card.html, then include it with {render card}. Relative names resolve beside the calling template. {render /shared/card} selects site/shared/_card.html.

Settings and structured data

Public settings live under app in .flea.config.json. Use {app.site_name} in your templates. A file named flea/data/team.json is available as data.team.

{#if app.phone}
  <p>Call {app.phone}</p>
{/if}

{#each data.team.members as member}
  <p>{member.name}</p>
{:else}
  <p>Meet the team soon.</p>
{/each}

Conditions take dotted paths, not JavaScript expressions. Use {#unless app.phone}...{/unless} for a negative condition. Both support {:else} and {:else if dotted.path}.

Make content editable

A snip is a piece of content the admin can change. Mark an element with a bare snip attribute:

<section snip>
  <h2>Made just around the corner.</h2>
  <p>Visit our studio on Saturday.</p>
</section>

Dev extracts the inner HTML into JSON and replaces it with a generated snip directive. Let Flea generate the ID and keep it unchanged. The JSON entry becomes the source of the editable value.

Classes, layout and other attributes stay in the template. Don't nest snips or put template directives inside a new editable region. Use dedicated image and video snips for media.

Admins can format text and edit page titles and descriptions using Page details. Changes are published with the page's Save button.

Photos & videos

Photos

<img snip src="/images/studio.jpg"
  alt="The studio in the afternoon"
  width="1200" height="800" />

Dev imports a local JPEG or PNG into managed media and creates the source and alt-text bindings. Keep dimensions, classes and links in your HTML. Don't combine a media snip with srcset, picture or competing source elements.

Admins click a photo in Edit mode to choose or upload a replacement. Save publishes it; Cancel discards the draft.

Videos

<video snip src="/videos/studio.mp4" controls></video>

Use a fast-start MP4 with H.264 video and optional AAC-LC audio, up to 25 MiB. Flea does not transcode videos. Admins can replace the video or its poster from the page editor.

Video storage is limited to 64 MiB, including retained replacements. Managed MP4 files are Git-ignored. Restore missing files on a fresh checkout with flea pull --snips-only before validation.

Repeatable content

A multisnip lets an admin add, remove and reorder items such as team members. Give the group a name and name its editable fields:

<article multisnip="team">
  <h2 snip="name">Sam Rivera</h2>
  <p snip="title">Studio founder</p>
  <img snip="photo" src="/images/sam.jpg" alt="Sam" />
</article>

Dev turns the seed into a loop. Admins use the on-page Add tile, remove button and drag handles. Arrow keys on a handle can reorder items too.

Keep each group on an individual page, with one root element. Don't nest groups or place them in layouts, partials or other loops. Video fields are not supported in multisnips.

Hand over the editing

Add an approved admin from your site folder:

flea admin admin@example.com

This adds the address to admin.emails. Admins visit /admin and sign in with an emailed code. All approved admins have the same editing access.

Editing starts enabled. Click text or media, make changes, then use Save or Cancel. Both keep editing on. Save updates the page in place without reloading it; Cancel returns to the latest successful save.

New local sites preview email in the browser without sending it. Production needs HTTPS and real email delivery. Commit and deploy admin-list changes before sharing the live sign-in link.

Sessions have a default 30-day idle window. Set admin.session_idle_days to a value from 1 to 365. An empty admin list disables live sign-in.

Your CSS, your design

Generated sites include Prewind 1.3.1. Start with global styles, then use utilities for individual adjustments. There is no CSS build step.

Edit site/css/theme.css for colors, fonts and spacing tokens. Put shared rules in site/css/global.css inside @layer styles. CSS stays in source and is published by normal deployment.

Icons

{icon arrow-right}
{icon search size="20" aria-label="Search"}

Dev downloads only the referenced Lucide icons into flea/icons/. Commit the cache for offline use. Status checks do not download icons.

Put your site online

Flea hosts multiple sites on one Ubuntu server. You'll need SSH access, a domain pointing to that server, and inbound TCP ports 80 and 443 for HTTPS.

Set up the server

flea setup

Run this from your computer and point it at a blank Ubuntu server over SSH. Flea installs the bundled server there and prepares the host to serve your sites. There is nothing to install by hand — no Go, Node, Python or database on the host. Use a server with ports 80 and 443 available for HTTPS.

Deploy a branch

flea deploy

The first run asks for the server, domain and HTTPS preferences. It saves that branch's destination in .flea.config.json and offers to commit your reviewed files. Deployment publishes committed source and requires a clean working tree.

Each branch has its own destination. Use flea deploy -configure to change it, or flea https -configure to revisit just the HTTPS settings. Configuring a destination does not create DNS records.

Keep admin changes

Normal deployment preserves live editable content and publishes committed CSS. To bring those edits into your local project, stop dev and run:

flea pull

Pull retrieves live content and referenced media. Review and commit the result.

To deliberately publish local content edits, first establish a pull baseline, then run:

flea deploy --with-snips

Conflicts require an explicit choice between the live and local changes.

Email & contact forms

New sites set dev.email_preview to true. Local sign-in and contact emails open as private browser previews without Resend credentials. Preview messages expire and disappear when dev stops.

For real delivery, run:

flea email

Local credentials belong in the private, Git-ignored .env file. For real local delivery, set the preview toggle to false and restart dev. Production ignores the preview toggle and needs server-side mail configuration.

A contact form

Enable the bundled Contact app under apps.contact in .flea.config.json, with a mount and the recipient in email.to. This replaces the removed top-level contact settings and the old /_flea/contact route: there is no alias or automatic migration, and deploy with a current server; 0.19.0 uses deployment protocol 27. Create site/contact/index.html and a mount-relative site/contact/thank-you.html. The form includes an explicit CSRF control and posts to the mount:

<form method="post" action="/contact">
  {csrf}
  <label>Name <input name="name" required maxlength="100" /></label>
  <label>Email <input type="email" name="email" required /></label>
  <label>Message <textarea name="message" required maxlength="5000"></textarea></label>
  <div hidden><label>Leave empty <input name="website" tabindex="-1" autocomplete="off" /></label></div>
  <button type="submit">Send message</button>
</form>

Success redirects to the mount's thank-you page with a visitor-bound notice. Messages are emailed, not stored, and validation re-renders the form with safe values on error. There is no general-purpose form backend.

Email templates

Customize mailers/*.email.html and *.email.txt. HTML emails share mailers/main.layout.html. Keep its slot and use escaped app.* and email.* values.

flea email preview sign-in

This renders a sample without sending an email.

Enable a blog

Blog is an optional built-in content application. It adds a public post list and individual post pages, plus a basic admin editor using Flea’s existing sign-in, rich text and photo library. No database or extra service is required.

Requires Flea 0.15.0 or newer and a current server. The public installer downloads 0.19.0, which includes Blog, and 0.19.0 uses server protocol 27. Enable it explicitly in each site; a CLI update does not change existing project files.

1. Enable it in your site configuration

Merge this into .flea.config.json, preserving your other settings and apps:

{
  "apps": {
    "blog": {
      "mount": "/blog"
    }
  }
}

The mount owns /blog and its entire URL subtree, so ordinary pages and assets cannot occupy those URLs. Removing the Blog configuration disables its routes without deleting stored posts.

2. Add the templates

Sites created with Flea 0.15.0 include these private templates. For an existing site, generate a fresh temporary site with the matching CLI and copy these files, preserving your site’s custom layout:

  • site/blog/_index.html for the public list.
  • site/blog/_post.html for individual posts.
  • site/admin/blog.html and site/admin/blog-edit.html for the admin screens.

Copy the Blog rules from the fresh site’s site/css/global.css into your own stylesheet. Keep your existing styles and layout. If you choose another mount, move the two public templates under that directory while keeping their private filenames. Add an admin link to /admin/blog, or visit it directly.

3. Preview, commit and deploy

flea dev
# Check your site locally, then stop dev and commit the changes.
flea deploy

Both the local CLI and the destination server need the matching version. An explicit flea update-server updates the shared server and briefly restarts every site on that host; back up first. Updating a server does not add Blog templates or enable Blog on existing sites.

Create and publish posts

Sign in at /admin, then open /admin/blog. Choose New post, enter a title, slug, excerpt and rich body, and optionally select or upload a cover photo. Save creates a draft. Publish makes it public; Unpublish makes it private again. Saving an already published post updates it immediately. Cancel discards unsaved changes.

Published posts appear at /blog and /blog/<slug>. Draft text stays out of public routes and template data, and a draft URL returns 404. Photo files are public assets, including covers attached to drafts. Covers use the existing JPEG/PNG photo processing; inline body photos are not supported.

Leave the publication date empty to assign it when first publishing, or enter an RFC3339 date such as 2026-10-13T14:00:00Z. A future date publishes immediately, not on a schedule. Lists show the newest publication dates first. Changing a slug changes the URL without creating a redirect.

Post JSON for agents and developers

The add-blog agent skill documents this setup and the supported template values.

Posts use the optional top-level blog array in flea/snips.json. Preserve the existing pages, shared, archive and media values. Here is one draft post:

{
  "blog": [
    {
      "id": "a7Km2pQ9xB",
      "title": "Welcome",
      "slug": "welcome",
      "excerpt": "Our first article.",
      "body": "<p>Welcome to our website.</p>",
      "status": "draft"
    }
  ]
}

Keep the ten-character, case-sensitive alphanumeric ID stable through edits. Slugs must be unique across drafts and published posts, using lowercase letters, digits and separating hyphens, up to 100 characters. Titles are required and limited to 200 characters; excerpts to 500. The limit is 200 posts and 1 MiB per body, within the existing 5 MiB content file. Status is draft or published; published records require published_at. An optional cover references an existing ID in the media map, never a filename or URL.

Template values

The listing template can iterate published posts:

{#each blog.data.posts as post}
  <article>
    <h2><a href="{post.url}">{post.title}</a></h2>
    <p>{post.excerpt}</p>
  </article>
{:else}<p>No posts yet.</p>
{/each}

The post template receives blog.data.post, including title, excerpt, URL, publication date, body and an optional cover object with src, alt, width and height. The listing URL is blog.data.url.

<h1>{blog.data.post.title}</h1>
<time datetime="{blog.data.post.published_at}">
  {blog.data.post.published_label}
</time>
<div>{blog.data.post.body}</div>

Only the exact {blog.data.post.body} directive renders sanitized rich HTML, and only in ordinary element content. Other values remain escaped. Never put the body directive in an attribute, script or textarea. Braces inside a post body are ordinary text, not template source.

Keep live edits when deploying

Normal flea deploy preserves live posts by ID and seeds new source-only IDs. Before an agent edits existing live posts in Git, run flea pull. Publish reviewed source changes with flea deploy --with-snips; this existing flag includes Blog records and cover metadata. Conflicting edits require a whole-post choice, and noninteractive conflicts stop.

Omitting a post from source never deletes its live record. Unpublish it to remove its public page. Backups include live posts and covers; rollback keeps current content while selecting earlier code. Comments, categories, tags, search, scheduling and revision history are deferred.

Apps

Blog is a built-in content application available from 0.15.0; see Blog setup. The service contract below applies to apps such as Contact, rather than Blog’s content storage and admin editor.

An app is a small, separate JSON service mounted at a public URL. Flea owns the public page, the HTML form, the redirect, the template values and the email; the app owns its own logic and validates its own fields. Values an app returns are request-local and are never written into your site.

Contact ships with Flea. You can also register your own managed local app package. See Building a custom app.

What you can use

  • Contact sends a visitor's message to one email address. Its configuration, form and templates are in Email & contact forms.
  • Custom apps are managed local executables registered under apps.<name> with a validated package. They can own their own sessions.
  • Remote services, public read-only routes declared in config, databases and uploads are not part of the shipped contract.
  • There is no public SDK. Flea's Go packages are private, but an app is an ordinary executable that speaks the documented HTTP/JSON contract.

Enable Contact

Merge this into .flea.config.json, keeping your other settings:

{
  "apps": {
    "contact": {
      "mount": "/contact",
      "email": {"to": "owner@example.com"}
    }
  }
}

mount is required: a canonical public path such as /contact or /deep/contact. email.to is required. Optional email.from overrides the server sender and must be authorized by your mail provider. Credentials never belong here. Remove the apps.contact entry to disable the app.

Create site/contact/index.html and a mount-relative site/contact/thank-you.html. Do not also create site/contact.html. The starter includes both pages but leaves the app disabled until you choose a recipient. Restart dev after changing app settings.

How a submission flows

  1. The visitor submits an ordinary HTML form to the mount.
  2. Flea checks CSRF, exact Origin, method, content type and size, then converts the fields to flat JSON.
  3. Flea calls the app's mount-relative route with its own private credential. Browser cookies and authorization are never forwarded.
  4. The app returns JSON. Flea redirects, re-renders with errors, or shows a safe unavailable message.

App values appear under the app name, such as contact.data.name, contact.invalid.email, contact.error and contact.flash.notice. They are escaped values, never template source.

Building a custom app

You can write an independent HTTP service that speaks the current Flea App Protocol (version 2) in any language, then register it as a managed local executable. It receives flat JSON and returns a small JSON envelope. This section documents the contract so you can build, mount and test one.

Custom apps are available from 0.17.0. Add an apps.<name> entry with a mount, and put a validated package at flea/apps/<name>/ containing app.json and the executables it names. There is no install command, no package registry, no url or port key and no public SDK. Flea launches only this confined local executable; remote services are not supported. Deploying an app package requires server protocol 27, so update the server first; a protocol-25 server refuses the package.

Register a package

Build your service for the server platform, then create a package. The manifest's name must match the config key, protocol must be 2, and executable maps a <goos>-<goarch> key to one filename in the same directory. Build for every platform you run (your development host and the server) and list each one:

flea/apps/session/app.json
{"name":"session","version":"0.1.0","protocol":2,"executable":{"darwin-arm64":"session-darwin-arm64","linux-amd64":"session-linux-amd64"}}
flea/apps/session/session-darwin-arm64
flea/apps/session/session-linux-amd64

Enable it in .flea.config.json:

{
  "apps": {
    "session": {"mount": "/session"}
  }
}

Create a page at the mount, such as site/session/index.html. A GET reads from the app; a POST submits a form that includes {csrf}. Flea strips the mount, so /session/login calls service route /login. Restart flea dev after changing app settings or rebuilding the executable. At handshake time Flea verifies the running service, so the manifest is not trusted as proof of compatibility.

Two boundaries

Keep the browser-to-Flea form boundary separate from the Flea-to-app call. The form is URL-encoded and bounded to 32 KiB; only POST carries a body. Flea strips the configured mount and forwards the rest of the path unchanged, so the mount itself becomes /.

Request JSON

There is no request envelope. The body is a flat object of form names:

{"name":"Alex","email":"alex@example.com","message":"Hello"}
  • A name submitted once is a string. A repeated name is an array of strings.
  • An empty field stays ""; a missing field is absent.
  • Names are literal: address.city and items[0] stay those exact keys, with no nesting.
  • Values are always strings or arrays of strings. The app converts types itself.
  • Flea verifies and removes its own _csrf field before forwarding. An app must not define it.
  • The JSON body is bounded to 192 KiB.

Response envelope

The service replies with one JSON object using only these keys:

  • data (object): app-owned values, rendered as contact.data.*.
  • invalid (object of string to string): validation messages, contact.invalid.*.
  • error (string): one operational failure message, contact.error.
  • flash (object of string to string): temporary messages, contact.flash.*.
  • redirect (string): a mount-relative destination, handled by Flea and not shown in templates.
  • session (object or null): an app-owned session instruction, not shown in templates. See App-owned sessions.

Only these keys are reserved. Unknown keys, an explicit null (except for session, where null clears the cookie), duplicate keys, a non-object body, a wrong content type or an oversized body are treated as a service failure. invalid and flash values must be strings; values inside data may be any JSON. Flash is limited to 4,096 bytes and responses to 1 MiB.

Statuses and browser outcomes

  • 200 with no invalid and no error: success. With redirect, the browser gets a 303.
  • 422 with at least one invalid and no error: the page re-renders with status 422.
  • 503 with an error and no invalid: the page re-renders with status 503.
  • Any other status or a malformed response becomes a safe 503 with a generic message.

Success:

{"redirect":"thank-you","flash":{"notice":"Your message was sent."}}

Validation:

{"data":{"email":"invalid"},"invalid":{"email":"Enter a valid email address."}}

Failure:

{"error":"We couldn't confirm delivery. Please try again later."}

Launch contract

Flea launches a managed app itself; a site configures only apps.<name>.mount and never a port, descriptor or token. The child receives three inherited descriptors:

  • fd 3: an already-bound 127.0.0.1:0 TCP listener, so there is no port race and no port in config.
  • fd 4: one JSON object with exactly five string keys: {"Name":"<app>","Token":"<64 hex>","Storage":"<private dir>","CapabilityURL":"","CapabilityToken":""}. A custom app gets empty capability values; the bundled Contact app gets a non-empty capability URL and token. Unknown fields are rejected, so declare all five.
  • fd 5: a parent-liveness pipe; EOF means shut down.

The child environment is only LANG=C, and its standard output and error are discarded so private payloads are never logged. The executable is re-opened through a confined root at launch, checked against the size and SHA-256 recorded when the site loaded, and copied to a private file before it runs; a swap after validation cannot change what runs. One child runs per site and app with bounded backoff; an unavailable app only affects its own routes.

Handshake and transport

Before any app call, Flea performs a private handshake:

GET /_flea/handshake
Authorization: Bearer <app-token>

The service must return 200 with JSON like:

{"name":"example","version":"0.1.0","protocol":2}

Flea checks the name and protocol: 2; version is the app's own release. A manifest alone is not proof. Every call carries the bearer token; browser cookies and authorization are never forwarded. Responses must be application/json, redirects are not followed, and POSTs are never retried. The handshake deadline is 2 seconds and ordinary calls 15 seconds; at most four calls run per app and 64 process-wide, with no waiting queue.

App-owned sessions

A custom app can own its own server-side sessions; Flea stores no session data. Flea reads its own per-app cookie and sends the opaque token to the app as the X-Flea-Session request header, never as a browser cookie or authorization header. The app's reply may add a session key: omit it to leave the cookie unchanged, use null to clear it, or set {"token":"...","max_age":86400} to set or rotate it. Tokens are 16 to 512 cookie-safe printable ASCII bytes and max_age is 1 second to 30 days. A malformed session value is rejected and no cookie changes. Flea owns the cookie name, Secure, HttpOnly, SameSite=Lax, Path=/ and the __Host- prefix. The cookie is isolated by app, and by site through host-only scoping, so a production cookie is never sent to another site's host; a malformed or duplicate cookie, including a valid cookie with a malformed duplicate of the same name, is ignored. The token never appears in templates, logs, URLs or public JSON. Store session state in the private directory Flea passes to the app at launch. It is stable per-site runtime state outside every release, excluded from releases and backups, and never pruned by Flea, so it survives a release change; back it up yourself. An app session never grants admin or editor access.

A complete managed sample

This standard-library program is a whole managed app: it reads the inherited descriptors, answers the handshake, serves a page, and owns a session cookie. Copy it into an empty directory with go.mod, build it for every platform you run, and register the package as shown above. It imports no Flea package.

// A complete managed Flea app using only the standard library. Build it for
// every platform you run, place the files under flea/apps/<name>/, and register
// the package under apps.<name> in .flea.config.json. Flea launches it and speaks
// the contract below; it never imports a Flea package.
package main

import (
	"context"
	"crypto/rand"
	"crypto/subtle"
	"encoding/hex"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net"
	"net/http"
	"os"
	"os/signal"
	"path/filepath"
	"sync"
	"syscall"
	"time"
)

const (
	protocol      = 2
	version       = "0.1.0"
	sessionHeader = "X-Flea-Session"
	maxAge        = 3600
	maxSessions   = 1000
)

// fd 4 is one JSON object with exactly these five string keys. A custom app
// receives empty capability values; unknown fields are rejected.
type launchConfig struct {
	Name, Token, Storage, CapabilityURL, CapabilityToken string
}

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	if err := run(ctx); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

func run(ctx context.Context) error {
	configFile := os.NewFile(4, "app-credentials")
	var cfg launchConfig
	decoder := json.NewDecoder(io.LimitReader(configFile, 4097))
	decoder.DisallowUnknownFields()
	err := decoder.Decode(&cfg)
	var extra any
	end := decoder.Decode(&extra)
	configFile.Close()
	if err != nil || end != io.EOF || len(cfg.Token) != 64 {
		return errors.New("invalid launch configuration")
	}
	name := cfg.Name
	if name == "" {
		name = "example"
	}

	listenerFile := os.NewFile(3, "app-listener")
	listener, err := net.FileListener(listenerFile)
	listenerFile.Close()
	if err != nil {
		return errors.New("app listener is unavailable")
	}
	defer listener.Close()

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()
	alive := os.NewFile(5, "app-parent")
	defer alive.Close()
	go func() { _, _ = io.Copy(io.Discard, alive); cancel() }()

	app := newHandler(name, cfg.Token, cfg.Storage)
	server := &http.Server{
		ReadHeaderTimeout: 2 * time.Second,
		ReadTimeout:       15 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       30 * time.Second,
		MaxHeaderBytes:    16 << 10,
		Handler:           app,
	}
	done := make(chan error, 1)
	go func() { done <- server.Serve(listener) }()
	select {
	case err := <-done:
		return err
	case <-ctx.Done():
	}
	shutdown, finish := context.WithTimeout(context.Background(), 2*time.Second)
	defer finish()
	if err := server.Shutdown(shutdown); err != nil {
		server.Close()
	}
	<-done
	return nil
}

// handler is a tiny session service. The "login" action is a demonstration
// only: it checks no credentials and is never real authentication.
type handler struct {
	name    string
	token   string
	path    string
	mu      sync.Mutex
	tokens  map[string]int64
}

func newHandler(name, token, storage string) *handler {
	h := &handler{name: name, token: token, tokens: map[string]int64{}}
	if storage != "" {
		h.path = filepath.Join(storage, "sessions.json")
		if data, err := os.ReadFile(h.path); err == nil {
			_ = json.Unmarshal(data, &h.tokens)
		}
	}
	return h
}

func (h *handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	if len(r.Header.Values("Authorization")) != 1 ||
		subtle.ConstantTimeCompare([]byte(r.Header.Get("Authorization")), []byte("Bearer "+h.token)) != 1 {
		http.Error(w, "Unauthorized", http.StatusUnauthorized)
		return
	}
	if r.URL.RawPath != "" || r.URL.RawQuery != "" {
		writeJSON(w, 400, map[string]any{"error": "Unsupported request."})
		return
	}
	if r.URL.Path == "/_flea/handshake" && r.Method == http.MethodGet {
		writeJSON(w, 200, map[string]any{"name": h.name, "version": version, "protocol": protocol})
		return
	}
	if r.URL.Path != "/" {
		writeJSON(w, 404, map[string]any{"error": "Unsupported request."})
		return
	}
	switch r.Method {
	case http.MethodGet:
		token := r.Header.Get(sessionHeader)
		body := map[string]any{"data": map[string]any{"authenticated": h.valid(token)}}
		if token != "" && !h.valid(token) {
			body["session"] = nil
		}
		writeJSON(w, 200, body)
	case http.MethodPost:
		h.post(w, r)
	default:
		w.Header().Set("Allow", "GET, POST")
		writeJSON(w, 405, map[string]any{"error": "Use GET or POST."})
	}
}

func (h *handler) post(w http.ResponseWriter, r *http.Request) {
	if r.Header.Get("Content-Type") != "application/json" {
		writeJSON(w, 400, map[string]any{"error": "Send JSON."})
		return
	}
	var fields map[string]any
	decoder := json.NewDecoder(http.MaxBytesReader(w, r.Body, 192<<10))
	if err := decoder.Decode(&fields); err != nil {
		writeJSON(w, 400, map[string]any{"error": "Invalid body."})
		return
	}
	action, _ := fields["action"].(string)
	switch action {
	case "login":
		token, err := h.create()
		if err != nil {
			writeJSON(w, 503, map[string]any{"error": "Could not start a session."})
			return
		}
		writeJSON(w, 200, map[string]any{"data": map[string]any{"authenticated": true}, "session": map[string]any{"token": token, "max_age": maxAge}})
	case "logout":
		if err := h.drop(r.Header.Get(sessionHeader)); err != nil {
			writeJSON(w, 503, map[string]any{"error": "Could not end the session."})
			return
		}
		writeJSON(w, 200, map[string]any{"data": map[string]any{"authenticated": false}, "session": nil})
	default:
		writeJSON(w, 422, map[string]any{"data": fields, "invalid": map[string]string{"action": "Use login or logout."}})
	}
}

func (h *handler) valid(token string) bool {
	if token == "" {
		return false
	}
	h.mu.Lock()
	defer h.mu.Unlock()
	h.expire()
	_, ok := h.tokens[token]
	return ok
}

func (h *handler) expire() {
	now := time.Now().Unix()
	for token, expiry := range h.tokens {
		if expiry <= now {
			delete(h.tokens, token)
		}
	}
}

func (h *handler) create() (string, error) {
	var raw [32]byte
	if _, err := rand.Read(raw[:]); err != nil {
		return "", err
	}
	token := hex.EncodeToString(raw[:])
	h.mu.Lock()
	defer h.mu.Unlock()
	h.expire()
	if len(h.tokens) >= maxSessions {
		return "", errors.New("full")
	}
	h.tokens[token] = time.Now().Add(maxAge * time.Second).Unix()
	if err := h.save(); err != nil {
		delete(h.tokens, token)
		return "", err
	}
	return token, nil
}

func (h *handler) drop(token string) error {
	if token == "" {
		return nil
	}
	h.mu.Lock()
	defer h.mu.Unlock()
	previous, ok := h.tokens[token]
	if !ok {
		return nil
	}
	delete(h.tokens, token)
	if err := h.save(); err != nil {
		h.tokens[token] = previous
		return err
	}
	return nil
}

// save writes durably and returns any failure so the request can fail closed.
func (h *handler) save() error {
	if h.path == "" {
		return nil
	}
	data, err := json.Marshal(h.tokens)
	if err != nil {
		return err
	}
	dir := filepath.Dir(h.path)
	f, err := os.CreateTemp(dir, ".sessions-")
	if err != nil {
		return err
	}
	temp := f.Name()
	defer os.Remove(temp)
	if _, err = f.Write(data); err == nil {
		err = f.Sync()
	}
	if closeErr := f.Close(); err == nil {
		err = closeErr
	}
	if err != nil {
		return err
	}
	if err = os.Rename(temp, h.path); err != nil {
		return err
	}
	directory, err := os.Open(dir)
	if err != nil {
		return err
	}
	defer directory.Close()
	return directory.Sync()
}

func writeJSON(w http.ResponseWriter, status int, body any) {
	w.Header().Set("Content-Type", "application/json")
	w.Header().Set("Cache-Control", "no-store")
	w.WriteHeader(status)
	_ = json.NewEncoder(w).Encode(body)
}

Try the contract locally

A compatible service can be tested without Flea. The essential flow is: require a bearer token, answer GET /_flea/handshake with the identity above, and answer POST / with an envelope. For example, a local service could answer a handshake:

curl -s http://127.0.0.1:8787/_flea/handshake \
  -H "Authorization: Bearer $APP_TOKEN"

and a form submission:

curl -s -X POST http://127.0.0.1:8787/ \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Alex"}'

This proves the wire contract, authentication and statuses. It does not mount the service in a site.

What remains planned

Remote (non-local) services, public read-only routes declared in configuration, databases, storage helpers and file uploads remain planned. Flea supervises only a confined local executable; it does not download packages or run arbitrary commands.

Keep staging out of search

From FleaCMS 0.19.0, configure indexing for an already registered hostname over SSH. Staging and production can serve the same website files:

flea server indexing root@server staging.example.com noindex
flea server list root@server

Type the exact hostname when asked. Flea sends X-Robots-Tag: noindex, nofollow on that hostname's pages, assets, app responses, errors, downloads and redirects. Aliases can have different policies. The command restarts the shared service, briefly affecting other sites.

Policy belongs to the server, outside site app settings, editable content and release files. Normal deployment, content sync, code rollback and site restore retain the current policy. flea status and flea server list show effective settings. Existing hostnames without a policy keep their behavior; Flea does not infer staging from the hostname.

flea server indexing root@server staging.example.com allow

allow stops adding the framework restriction. It does not emit index, follow, remove owner-authored headers or meta tags, or guarantee search visibility. Each exact registered hostname is configured separately; wildcards and arbitrary forwarding headers cannot select a policy.

Keep robots.txt crawlable. A site-wide Disallow: / can stop crawlers discovering the noindex header. Flea leaves robots.txt, sitemaps, canonicals and templates unchanged and reports a warning for detected static site-wide crawl blocks. This controls cooperative search indexing, not private access.

Removing a site clears only its own hostname policies; redeploying a removed name does not restore them. Site backups exclude host policy. Interrupted policy changes use the existing server-side sudo flea-server -recover journal, which restores the complete prior host configuration. Upgrade both client and server to protocol 27 before using this feature. Verify the live staging header before removing any existing site-level meta fallback.

Backups & recovery

Make a backup

flea backup ../before-redesign.flea-backup

This downloads the active site's code and editable content, including managed media and source CSS. Choose a new file path outside your site and keep a separate copy. Credentials, certificates, deployment mappings, host indexing policies and sessions are excluded.

Roll back code

flea rollback --list
flea rollback

Rollback republishes earlier code and CSS while retaining current admin content and host indexing policy. It asks for confirmation before acting.

Restore a backup

flea restore ../before-redesign.flea-backup

Restore replaces live code, site configuration and editable content while retaining current host indexing policy. It requires typed confirmation. Take a fresh backup first if newer content matters.

Reset a local project

flea reset returns the local site to a clean starting point after confirmation. It replaces local files and settings, keeping Git history and a private sibling backup. It does not reset a live site.

Keep Flea up to date

Update your installed CLI with:

flea update

Flea verifies the downloaded checksum and version before replacing the executable. A local update does not update your remote host. From a configured site, explicitly run:

flea update-server

After confirmation, a terminal spinner shows that the update is running. Redirected output uses plain progress text; animation yields to SSH diagnostics and interactive sudo prompts. Successful updates print a completion message. Server updates affect every site on that host and ask before restarting it. Keep backups and check compatibility first. An interrupted update can be recovered with flea update-server --recover.

AI-assisted development

Flea projects include portable instructions so coding agents can follow the site's conventions and preserve existing content. For a focused addition, ask your agent to “add a blog”, “let's create a blog” or “add a contact form”. The project's AGENTS.md directs it to the matching skill.

The two setup skills ship in newly generated sites from 0.15.1. The public installer downloads 0.19.0. Blog requires 0.15.0 or newer; 0.19.0 uses server protocol 27.

  • flea/skills/add-blog/SKILL.md covers Blog setup, private list/post templates, navigation, post JSON, drafts and publishing. It documents blog.data.posts, blog.data.post and the exact rich-body directive {blog.data.post.body}.
  • flea/skills/add-contact-form/SKILL.md covers Contact setup, the form and thank-you page, exact field names, {csrf}, contact.data.*, contact.invalid.*, contact.error and contact.flash.notice. It also explains private email templates and local email previews.
  • flea/skills/import-brochure/SKILL.md guides imports and redesigns through content inventory, two design directions, a sample page, local assets and editable snips.
  • flea/skills/fleacms-site/SKILL.md covers research-first site building with real assets and design-review checkpoints.

A focused Blog or Contact addition follows your existing design without restarting a full-site consultation. Agents read the Markdown instructions; no plugin, account or runtime keyword listener is required.

Use the skills in an existing project

A CLI update leaves your project's files intact. Generate a disposable site with a matching 0.15.1-or-newer CLI, then copy flea/skills/add-blog/ and flea/skills/add-contact-form/ into your project. Add the matching request routes to your own AGENTS.md, preserving its custom rules. You can also point an agent directly at either SKILL.md.

These guidance files stay in Git but are excluded from public serving and deployment. A skill does not grant permission to publish posts, send real test mail or deploy.

Where Flea fits

Flea is built for small content websites. It is not a general application framework or an ecommerce platform.

  • No general field schemas, arbitrary server-side application code or general-purpose form backend.
  • Custom apps are managed local executables only: no remote services, package registry or public SDK. Each app owns and protects its own storage.
  • No video transcoding or video fields in collections.
  • No content revision-history interface. Use the backup and recovery commands.
  • Rich text is sanitized; editable content does not accept unrestricted HTML.
  • Downloads currently cover Apple Silicon macOS and x86-64 Linux. Clean-machine testing is in progress.

The source repository is private. The binaries are free to use, without an account or license key.
